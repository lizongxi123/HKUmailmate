# 开发规范手册

适用项目：双人协作的 NLP 邮箱 Agent 平台。状态：初始规范，业务代码与工具配置尚未建立。

本文中的“必须/禁止”是执行要求；“建议”允许根据任务调整并说明原因；“待定”需要在相关功能实施前作出决定。接口表属于目标契约，不代表接口已经实现。

## 1. 目标、范围与决策

第一版实现用户注册、登录、退出、当前用户查询，以及邮箱绑定、状态查询、解绑和少量邮件读取验证。后续再实现邮件摘要和回复草稿。

已确定：Python、FastAPI、React、单体应用、任务分支与 PR、CI 通过后作者可自行合并。数据库产品、前端语言、运行时版本、包管理器、认证方式、邮箱服务商、模型和部署方式待定。

不提前引入微服务、消息队列、复杂权限系统或通用 Agent 框架。需要新增框架、基础设施或更改重要技术选型时，在 `docs/decisions/` 记录：背景、选择、替代方案、影响和日期。目录在首次记录时建立。

## 2. 目录与代码职责

以下是业务代码建立时使用的基础布局，按实际需求逐步创建，不预建空壳：

```text
AGENTS.md
docs/
  DEVELOPMENT_STANDARDS.md
  decisions/
backend/
  app/
    main.py
    api/             # 路由、HTTP 请求和响应处理
    schemas/         # 对外请求/响应模型
    services/        # 业务流程
    repositories/    # 数据访问
    models/          # 持久化模型
    integrations/    # 邮箱、模型等外部服务适配
    core/            # 配置、认证基础设施、日志
  tests/
frontend/
  src/
    api/             # HTTP 客户端与接口调用
    components/      # 可复用界面组件
    pages/           # 页面
    hooks/           # 自定义 React Hooks
    features/        # 按业务组织的前端功能
```

- 路由不承载复杂业务逻辑，不直接拼装数据库查询。
- Service 不依赖 FastAPI 的 Request、Response 或 HTTPException；业务异常在接口边界转换为 HTTP 错误。
- 数据访问层不执行 HTTP 响应处理；外部服务通过明确适配接口接入。
- 简单功能可省去无意义的转发层，但职责边界必须清楚。
- 不创建包罗万象的 utils 模块；工具函数按用途命名并放在所属模块。
- 禁止循环依赖；不为复用几行代码提前建立大型抽象体系。
- 异步路由中不得直接执行阻塞网络或数据库调用；选用匹配的异步客户端或明确的线程执行方式。

## 3. 命名与代码风格

### 3.1 Python

| 对象 | 规则 | 示例 |
|---|---|---|
| 模块、文件、包 | snake_case | `email_connections.py` |
| 变量、函数、方法 | snake_case | `get_current_user` |
| 类、异常、Schema | PascalCase | `EmailConnection`, `EmailAuthorizationError` |
| 常量、环境变量 | UPPER_SNAKE_CASE | `EMAIL_REQUEST_TIMEOUT_SECONDS` |
| 内部实现成员 | 前缀下划线 | `_refresh_access_token` |
| 布尔值 | is/has/can/should 等清晰前缀 | `is_active`, `has_connection` |

- 避免 `data1`、`temp`、`do_stuff` 等模糊名字；局部简单循环变量可简写。
- 单个资源使用单数，集合使用复数：`connection`、`connections`。
- 单位写入变量名：`timeout_seconds`、`size_bytes`；不要只写 `timeout` 后依赖猜测单位。
- Python 公共函数、公共方法的参数和返回值必须有类型标注；避免无理由使用 Any。
- 不用可变对象作默认参数，不依赖可变全局状态传递用户上下文。
- 格式交给工具配置，不人为争论空格和换行；具体工具与版本在后端初始化时确定。

```python
async def list_email_connections(
    user_id: UUID,
    limit: int = 20,
) -> list[EmailConnection]:
    ...
```

以上只演示命名与类型，不是完整实现，UUID 导入及模型定义由实际代码提供。

### 3.2 React / JavaScript / TypeScript

| 对象 | 规则 | 示例 |
|---|---|---|
| 变量、函数、属性 | camelCase | `connectionStatus`, `connectMailbox` |
| 组件、组件文件 | PascalCase | `EmailConnectionCard.jsx` 或 `.tsx` |
| 自定义 Hook | use 开头 | `useEmailConnections` |
| 普通模块、业务目录 | kebab-case | `email-client.js`, `email-connections/` |
| 类型、接口（若使用 TS） | PascalCase | `EmailConnection` |
| 模块级常量 | UPPER_SNAKE_CASE | `DEFAULT_PAGE_SIZE` |

- 组件使用函数组件；渲染逻辑不直接发起请求。
- API 调用集中在客户端模块，组件不散落重复 URL、凭证和错误解析逻辑。
- 组件处理展示与交互，业务状态放在对应功能或 Hook；不提前引入全局状态库。
- 若使用 TypeScript，开启严格类型检查；外部返回值仍需按边界校验，类型断言不能替代校验。
- API JSON 保持 snake_case；前端原样使用传输字段，若转换为 camelCase，统一在 API 边界处理，禁止各组件自行转换。

### 3.3 注释、文档与复杂度

- 标识符统一英文；团队说明、注释和文档默认中文，标准技术术语保留英文。
- 注释解释原因、约束和不明显的取舍，不重复代码字面意思。
- 公共业务函数存在复杂规则、异常或副作用时写 Docstring；显而易见的简单函数无需模板化注释。
- 函数围绕一个明确职责；不设机械的行数上限，复杂分支出现时按职责拆分。
- TODO 必须说明缺失内容和影响；涉及安全与数据正确性的未完成逻辑不得用 TODO 代替实现。

## 4. HTTP API 契约

### 4.1 路径与方法

- 对外业务 API 使用 `/api/v1`；路径小写，多单词资源使用 kebab-case，资源优先用复数。
- GET 读取且不改变业务状态；POST 创建资源或执行明确动作；PATCH 局部更新；DELETE 删除或解除关联。
- 邮箱服务商要求的授权回调属于特殊协议入口，路径和方法按其协议确定；回调必须验证授权上下文。
- 不用 GET 触发邮件发送、解绑等业务写操作。

第一版目标接口：

| 方法 | 路径 | 用途 | 成功状态 |
|---|---|---|---|
| GET | `/api/v1/health` | 基础存活检查 | 200 |
| POST | `/api/v1/auth/register` | 注册 | 201 |
| POST | `/api/v1/auth/login` | 登录 | 200 |
| POST | `/api/v1/auth/logout` | 退出，具体失效机制随认证方案落实 | 204 |
| GET | `/api/v1/users/me` | 当前用户 | 200 |
| GET | `/api/v1/email-connections` | 当前用户的邮箱连接 | 200 |
| GET | `/api/v1/email-connections/{connection_id}` | 连接状态和公开信息 | 200 |
| DELETE | `/api/v1/email-connections/{connection_id}` | 解绑并停止后续访问 | 204 |

绑定流程、授权发起与回调、邮件读取接口，在邮箱服务商确定后补充契约。不要提前假定所有服务商采用相同 OAuth 或 IMAP 流程。需要检查数据库等依赖时另外定义就绪检查，不把基础 health 当成所有依赖可用的证明。

### 4.2 请求与响应

- JSON 字段统一 snake_case，HTTP 时间字段使用带时区的 RFC 3339 格式；对外统一 UTC，例如 `2026-10-26T11:00:00Z`。
- 标识符对外使用字符串；内部生成方式待数据库方案确定，不以 ID 难猜代替权限校验。
- 每个接口定义明确的请求、成功响应和错误 Schema；以 FastAPI 生成的 OpenAPI 为契约来源，避免另维护不一致的字段清单。
- 创建、更新、响应模型分开；不直接返回 ORM 对象的全部字段，使用响应模型白名单。
- 写入模型明确限制可设置字段，禁止客户端修改 `user_id`、权限和内部状态；明确未知字段处理策略，禁止静默接受可疑字段。
- 成功响应直接返回资源对象，不强制再套 `code/message/data`。204 必须无响应体。
- 请求字段区分省略、null、空字符串；PATCH 中省略表示不修改，null 仅在字段允许清空时有效。
- 输入设置长度、范围、枚举及数量限制；禁止依赖前端校验保护后端。

连接响应示例（目标格式，非现有数据）：

```json
{
  "id": "connection_example",
  "email_address": "demo@example.com",
  "provider": "example_provider",
  "status": "connected",
  "created_at": "2026-10-26T11:00:00Z"
}
```

连接状态至少区分 `connected`、`reauthorization_required`、`disconnected`；尚未探测成功时不得返回 connected。服务商暂时故障不直接等同用户授权失效。

### 4.3 错误与状态码

错误统一使用以下形状；HTTP 状态与错误语义保持一致，不用 HTTP 200 包装失败：

```json
{
  "error": {
    "code": "EMAIL_AUTHORIZATION_EXPIRED",
    "message": "邮箱授权已失效，请重新连接。",
    "request_id": "request_example"
  }
}
```

- `code` 为稳定的 UPPER_SNAKE_CASE 机器标识，前端按 code 处理，不解析 message。
- `message` 面向用户，不包含调用栈、SQL、令牌或上游完整响应。
- 字段校验错误可增加 `details`，仅包含安全的字段名、原因和规则，不回显密码等输入值。
- FastAPI 的请求校验错误、HTTP 异常和未处理异常都须转换为上述结构；未处理异常记录内部日志并返回通用信息。
- 响应通过 `X-Request-ID` 暴露请求标识；错误体中使用同一值。外部传入标识须校验格式与长度，或由服务端生成。

| 状态 | 适用情况 |
|---|---|
| 400 | 请求流程无效，例如授权上下文不匹配 |
| 401 | 未登录、登录凭证无效或过期 |
| 403 | 已认证但无权执行某类操作 |
| 404 | 资源不存在；对其他用户的私有资源同样返回 404 |
| 409 | 唯一约束或资源状态冲突 |
| 422 | 请求字段校验失败 |
| 429 | 请求被限流 |
| 500 | 未预期的内部错误 |
| 502/503/504 | 按实际情况表示上游失败、暂时不可用或超时 |

初期维护实际使用的错误码，不预先建立庞大错误码体系。注册冲突和登录失败的对外文案避免不必要的账号存在性泄露。

### 4.4 列表、分页与兼容性

- 普通数据库列表初期使用 `limit` 和 `offset`：默认 limit=20，允许 1–100，offset 不小于 0。
- 列表响应为 `{ "items": [], "limit": 20, "offset": 0, "has_more": false }`，不强制执行总数统计。
- 默认 `created_at` 降序、ID 降序作为稳定次序；可排序和过滤字段必须白名单校验，不接受任意 SQL 字段或表达式。
- 邮箱供应商的游标分页由适配层处理；对外邮件分页契约在读取功能实现前确定，不强行换算成 offset。
- 删除、重命名字段，改变类型、必填性或已有语义均视为不兼容变更，必须协调前后端并评估版本迁移。
- 增加可选字段通常可兼容，但仍须检查消费者；不得暗中改变默认排序或分页语义。

## 5. 数据库与数据归属

- 数据库及 ORM/迁移工具待选型；选定后统一使用，不由各模块分别引入。
- 用户私有数据包含不可为空的用户归属；关联记录通过外键或等价约束保证一致性。
- 根据明确业务规则建立唯一约束和索引，不能仅靠“先查询再插入”防止并发重复。
- 所有私有资源查询必须包含用户范围；访问、更新、删除、后台任务和 Agent 工具调用同样适用。
- 身份从后端认证上下文获取；创建请求不得自行指定所属用户。
- 相关多步写操作采用明确事务边界；外部网络请求不长时间占用数据库事务。
- 数据库调用参数化，禁止字符串拼接用户输入形成 SQL。
- 时间使用带时区值并统一 UTC；内部字段使用 `created_at`、`updated_at` 等明确名称。
- 每次数据库结构变更提交迁移文件；已被共享环境执行的迁移不得原地修改。
- 生产迁移前说明兼容性、备份和失败处理；优先先扩展再收缩，不假定所有迁移可安全降级。
- 解绑不默认删除历史邮件、摘要及草稿；保留和删除策略须在存储这些数据前明确，并向用户说明。
- 第一版读取验证优先最少持久化；不因“以后可能用到”保存完整邮箱内容或附件。

## 6. 注册、登录与权限

- 密码只保存使用成熟密码哈希库生成的哈希，不自行实现算法，不可逆加密存储登录密码。
- 注册和登录设置输入长度限制、密码要求及速率限制；具体认证方案实施时明确会话有效期和恢复策略。
- 登录失败返回统一文案，不区分账号不存在与密码错误；密码、会话标识不放入 URL。
- 认证中间件/依赖统一处理身份，业务代码不重复解析凭证；前端路由保护不能代替后端权限检查。
- 会话或令牌方案待定。若使用 Cookie，明确 HttpOnly、Secure、SameSite 和 CSRF 防护；若使用 Bearer，明确存储、刷新、吊销及 XSS 风险控制。
- 退出必须落实对应会话失效或令牌撤销语义，不仅清空页面状态；方案选择时说明已签发凭证何时真正失效。
- 对外访问使用 HTTPS，CORS 显式限制允许来源，不把任意来源与携带凭证访问同时放开。
- 不把密钥、邮箱令牌或用户敏感信息放入前端构建变量；浏览器打包内容均视为公开。

## 7. 邮箱接入与外部服务

- 先确定首个邮箱服务商、接入协议及可用权限，再实现绑定流程；第一版只申请读取所需的最小权限。
- OAuth 流程由后端验证 state，并将其与发起用户绑定、限制有效期及一次性使用；适用时使用 PKCE，回调地址采用固定配置或严格白名单。
- 不信任回调参数里的用户身份；授权码、令牌和邮箱密码不得进入 URL 日志或页面持久状态。
- 应用登录密码使用哈希；需要再次调用供应商的邮箱凭证使用可解密的安全存储，密钥与数据库分开管理，禁止混淆两类处理方式。
- 同一邮箱能否绑定多个平台用户，须在绑定功能实现前明确；通过数据库约束落实最终规则。
- 接入成功以服务商身份和实际调用结果确认，不信任前端提交的邮箱地址。
- 解绑必须停止后续访问，清除本地访问凭证；支持时撤销供应商授权，并说明撤销失败的处理方式。
- 所有外部调用设置超时和有限重试；只对适合重试的临时错误重试，采用退避并遵守限流提示。
- 不对授权失败无限重试；不对非幂等操作盲目重试。需要重试的写操作必须有去重方案。
- 用户可控的 IMAP 主机、远程图片和附件 URL 不得直接由服务器任意访问；此类能力实施前处理 SSRF、目标地址及大小限制。
- 不默认下载附件、不执行附件、不自动加载邮件远程图片；邮件 HTML 展示必须经过可信的清理流程，禁止直接渲染原始 HTML。

## 8. 后续 Agent 功能约束

本节为后续阶段的边界，不要求第一版提前建设 Agent 基础设施。

- 摘要 Agent 读取已获授权的邮件并输出摘要；回复 Agent 生成草稿。两者都不默认拥有发送或删除权限。
- 邮件、附件和模型输出均为不可信数据；邮件中的“忽略规则”“读取其他用户邮箱”等内容不能改变工具权限。
- 工具端独立执行用户归属和权限校验，不依赖提示词约束安全边界。
- 模型输入仅包含任务必需信息；私人邮件发送给第三方模型前明确供应商及数据处理方式。
- 输入设长度和数量上限，模型输出按结构校验；设置超时、调用次数及费用上限。
- 日志默认记录模型标识、提示词版本、耗时和用量，不保存完整私人提示词与邮件正文。
- 模型调用失败或输出无效时返回明确状态，不伪造摘要或声称邮件已处理。
- 将来增加发送能力时，必须单独设计用户确认、精确收件人与正文展示、权限及重复发送保护。

## 9. 异常、日志与配置

- 捕获可处理的具体异常；禁止空 catch、裸 except 或把所有失败返回为空列表。
- 不向业务层散播供应商原始错误；适配层转成稳定的内部错误类型，并保留安全的诊断上下文。
- 使用结构化日志，至少包含时间、级别、事件名、request_id；按需添加内部 user_id、connection_id、耗时和结果。
- 日志不包含密码、Cookie、Authorization、访问令牌、授权码、连接字符串、完整邮件正文和附件；邮箱地址按需脱敏。
- 同一异常避免多层重复记录；未预期错误在统一边界记录调用栈，对客户端隐藏。
- 配置集中读取，启动时校验必要项；生产缺少密钥时失败退出，不使用隐式默认密钥。
- `.env.example` 仅放占位值和字段说明；真实 `.env`、私钥、数据库备份及私有邮件数据加入忽略规则。
- 依赖通过项目配置声明并提交选定工具的锁文件；不把个人环境导出当作依赖设计。
- 前后端使用稳定且兼容的运行时版本；具体版本选择后写入文档、运行时配置和 CI。

## 10. 测试与 CI

- 测试覆盖业务行为和风险，不机械镜像实现。纯文档或格式调整无需新增业务测试。
- 后端测试按业务模块组织，Python 文件使用 `test_*.py`，测试名描述条件和结果。
- 外部邮箱、模型调用默认模拟；自动化测试不访问真实邮箱、不发送邮件、不产生模型费用。
- 数据库集成测试使用独立测试数据库；迁移、约束和事务相关测试不能只靠 Mock 验证。
- 前端验证加载、成功、空状态和错误状态；涉及权限的功能同时测试后端拒绝行为。
- 不设没有依据的全局覆盖率门槛；优先保证关键路径和回归测试。

第一版至少覆盖：

| 模块 | 关键场景 |
|---|---|
| 注册 | 正常注册、无效输入、重复账号、响应无密码字段 |
| 登录与退出 | 正常登录、错误凭证、过期会话、退出后的失效语义 |
| 用户隔离 | 未登录被拒绝；用户 A 无法读取、解绑或使用用户 B 的连接 |
| 邮箱授权 | 正常绑定、无效/过期授权、回调上下文不匹配与重放（若适用） |
| 邮箱访问 | 超时、限流、授权失效、解绑后不再访问 |
| 数据安全 | 响应不包含令牌；错误和日志不泄露凭证 |

CI 建立后检查后端 Lint、格式和相关测试，以及前端 Lint、构建；采用 TypeScript 时增加类型检查。需验证数据库行为时增加隔离的数据库测试环境。

当前没有依赖配置与检查脚本，本文不提供假定可用的执行命令。初始化后必须在此补充真实命令，并保证本地与 CI 使用相同配置。必需检查应使用稳定名称，禁止通过跳过任务或忽略失败制造“通过”。

## 11. Git 与双人协作

- 主分支为 main，不设长期 develop；所有变更走 PR，不要求人工审批。
- 分支使用 `feature/<topic>`、`fix/<topic>`、`docs/<topic>`、`refactor/<topic>`、`chore/<topic>` 或 `hotfix/<topic>`；必要时加开发者标识。
- 一个分支完成一个明确任务；避免同一 PR 混合功能开发、大范围格式化和无关依赖升级。
- Commit 使用 `<type>(<scope>): <description>`，scope 可省略；type 使用 feat、fix、refactor、docs、test、chore、perf、build、ci 或 revert。
- 示例：`feat(auth): add user registration`、`docs: define development standards`。
- PR 说明问题、变更和验证结果；涉及接口、迁移或配置时说明兼容性及人工步骤。
- 作者可在必需 CI 通过后 Squash Merge；不要求等另一人审批。合并后删除不再使用的任务分支。
- 禁止直接推送 main、强推 main、绕过必需 CI；紧急修复同样通过 PR。
- 远程仓库初始化时配置相应保护并验证实际生效；尚未配置时不得声称规则已经强制执行。
- 同步 main 后处理冲突，不覆盖对方修改；不对共享分支擅自重写历史。
- 同时修改认证、公共 Schema、依赖文件或迁移时，先沟通范围，减少相互覆盖。
- 已合并错误通过新的 revert PR 修复，不通过 reset 和强推重写 main。

## 12. 环境、发布与回滚

- 两名开发者使用独立 Linux 用户、SSH Key、Git 工作目录和虚拟环境，不共用 root 开发。
- 开发服务使用不同端口；数据库实例可共享，但开发者及环境的数据、账号和权限须隔离。
- 使用 Compose 时区分 project name，并检查宿主机端口、卷和显式命名资源不会发生冲突。
- 同一 CVM 上的开发与生产仅属于逻辑隔离；资源抢占和主机故障仍会共同影响，容量和隔离强度需实测。
- 数据库等内部服务不直接暴露公网；开发访问优先通过 SSH 隧道或受控入口。
- 生产目录与开发目录分开；不直接在生产目录编辑代码。
- 部署方式待定；第一版先验证开发和 CI 流程，不因合并自动发布生产。
- 正式发布记录 Git SHA、版本、构建产物、时间、配置与迁移要求；若采用容器，记录镜像 digest 并保留稳定产物，不只记录可变标签。
- 发布前检查数据库兼容性与备份，发布后验证服务健康和关键业务；健康检查不能替代业务验证。
- 回滚部署使用已验证的历史构建产物；数据库恢复单独设计并明确数据丢失影响。
- 生产操作、安全配置和破坏性数据库操作必须有明确授权；普通代码及文档编辑无需逐项重复确认。

## 13. 完成标准与维护

一个开发任务完成，应满足：

1. 验收范围已实现，没有夹带无关功能。
2. 相关输入校验、身份和数据权限检查已落实。
3. 相关检查已运行；无法运行的项目明确列出原因。
4. API、环境变量、迁移或使用方式变化已同步文档。
5. 没有引入真实密钥、私人邮件或明显调试残留。
6. 汇报修改、验证结果、剩余事项和必要人工步骤。

规范变更同样通过 PR。落地工具后，将以下待定项及时补齐：数据库与迁移工具、运行时版本、前端语言与包管理器、认证和退出机制、首个邮箱接入协议、实际检查命令、数据保留策略及部署方案。
